## Part 1: E2E Test Environment (002)

Entities extracted from the feature spec's Key Entities section. This feature adds no plugin domain logic, so these entities describe the test environment and its artifacts, not runtime plugin state.

### Entity Relationship Overview

```text
TestVault 1───1 BoardFile
TestVault 1───n StoryNote
TestVault 1───1 PluginInstall (artifacts)
DebugSession 1───1 TestVault (bound to it)
VerificationScript ──(runs against)──> DebugSession
VerificationScript 1───1 VerificationReport (produces)
VerificationReport 1───0..1 Screenshot (references)
```

### Test Vault

The isolated, self-contained vault directory at the repository root.

| Field | Type | Required | Validation / Notes |
|-------|------|----------|--------------------|
| `path` | string | yes | Fixed: `test-vault/` at repository root (FR-002-001). |
| `boardFile` | path | yes | `test-vault/Board.md` must exist and conform to the board file format (FR-002-002). |
| `storyNotes` | path[] | yes | Set of sample notes covering full and missing attributes (FR-002-003). |
| `pluginInstall` | path | yes | `test-vault/.obsidian/plugins/obsidian-usm-plugin/` with `manifest.json`, `styles.css`, `main.js` (FR-002-005). |
| `communityPluginsJson` | path | yes | `.obsidian/community-plugins.json` lists the plugin id so it is enabled (FR-002-005). |
| `baseline` | object | yes | Known board structure used as the verification expectation (see `contracts/test-vault-structure.md`). |

**Invariants**:
- Reproducible: re-creating from the repository yields an identical environment (FR-002-004). The only non-committed file is the built `main.js` (gitignored), regenerated by `e2e:setup`.
- Isolated: no file outside `test-vault/` is read or modified during a test run (SC-002-002).

### Board File

The `Board.md` note defining the map's structure and settings.

| Field | Type | Required | Validation / Notes |
|-------|------|----------|--------------------|
| `frontmatter.usm-board` | boolean | yes | Must be `true` to activate the map view. |
| `frontmatter.usm-release-order` | string | no | `appearance` (default) or `alphabetical`. |
| `frontmatter.usm-view` | string | no | `map` (default), `edit`, `preview`. |
| `storyLinks` | string[] | yes | Ordered wikilink list; order defines column grouping and release order. |

**Invariants**: Conforms to `specs/001-user-story-map/contracts/board-file-format.md`. Self-describing and readable without the plugin (Constitution Principle VI).

### Story Note

A sample note representing a single story on the map.

| Field | Type | Required | Validation / Notes |
|-------|------|----------|--------------------|
| `frontmatter.activity` | string \| wikilink | no | Missing → "Unassigned" activity column. |
| `frontmatter.task` | string \| wikilink | no | Missing → "Unassigned" task column. |
| `frontmatter.epic` | string \| wikilink | no | Missing → "Unassigned" epic section. |
| `frontmatter.release` | string \| wikilink | no | Missing → "Unassigned" release row; rendered as card badge. |
| `frontmatter.story` / `title` | string | no | Card title cascade (Story → title → alias → file name). |

**Invariants**: Conforms to `specs/001-user-story-map/contracts/story-file-format.md`. The fixture set MUST include at least one fully-attributed note and notes missing each attribute level, so defensive grouping is exercised (FR-002-003).

### Debug Session

A running Obsidian instance bound to the test vault with a CDP port active.

| Field | Type | Required | Validation / Notes |
|-------|------|----------|--------------------|
| `port` | number | yes | Default 9222; configurable via `--port` (FR-002-008). |
| `host` | string | yes | Fixed `127.0.0.1` (localhost only). |
| `vaultPath` | path | yes | Must equal the test vault path. |
| `ready` | boolean | yes | True when `http://127.0.0.1:<port>/json/version` responds. |

**State transitions**:
```text
absent --launch--> starting --probe-ok--> ready
absent --launch--> starting --port-conflict--> error(actionable)
ready --launch-again--> ready (idempotent: reports "already available", no duplicate)
```

### Verification Report

The machine-readable output of a verification run (FR-002-014).

| Field | Type | Required | Validation / Notes |
|-------|------|----------|--------------------|
| `status` | enum | yes | `pass` \| `fail`. |
| `checks` | object[] | yes | One entry per standard check: `{ id, name, passed, actual, expected, detail? }`. |
| `taskColumns` | number | yes | Counted `.usm-header-cell--task` elements (FR-002-011). |
| `screenshot` | string | yes | Relative path to the captured image (FR-002-012). |
| `reactivity` | object | yes | `{ detected: boolean, delayMs: number, boundMs: 5000 }` (FR-002-013, SC-002-006). |
| `errors` | string[] | no | Diagnostic messages (e.g., connection failure hint). |

**Invariants**: Emitted as JSON to stdout and written to `e2e/output/`. Exit code 0 on `pass`, non-zero on `fail` (agent-interpretable without manual review).

### Verification Script

The committed, versioned script performing the standard checks (FR-002-016).

| Field | Type | Required | Validation / Notes |
|-------|------|----------|--------------------|
| `path` | path | yes | `e2e/verify.mjs` (Node ESM, Node 22+). |
| `checks` | set | yes | Task-column count (FR-002-011), screenshot (FR-002-012), reactivity (FR-002-013). |
| `transport` | CDP | yes | `fetch` + global `WebSocket` against `127.0.0.1:<port>`; no NPM dependencies. |
| `output` | VerificationReport | yes | Machine-readable JSON (see above). |

**Invariants**: Standard checks are deterministic and repeatable; ad-hoc inspection beyond these checks is the agent's separate capability (FR-002-017), not part of this script.

## Part 2: Manual Test & Preview Workflow (003)

This feature adds no plugin domain logic, so there are no new domain entities or state machines. The entities below are the *workflow artifacts* the spec's Key Entities section names; their shapes are fixed by the contracts in `contracts/`.

### Verification skill

- **Shape**: a Markdown file with YAML frontmatter (`name`, `description`) at
  `.github/skills/usm-e2e/SKILL.md`.
- **Fields (frontmatter)**:
  - `name` — `usm-e2e` (stable identifier; do not rename once released).
  - `description` — one sentence, discoverable from the skill index; must
    mention: manual/E2E verification, the test vault, ad-hoc inspection,
    manual-assist, mobile emulation, on-demand preview.
- **Body sections (required)**: prerequisites; environment preparation
  (setup/launch); standard checks; ad-hoc inspection (the `inspect.mjs`
  command table); the manual-assist protocol (three modes); mobile scenarios
  (emulation sequence incl. the mandatory restore step); on-demand interactive
  sessions; known runtime side effects and clean-tree restore; ending a
  session cleanly.
- **Relationships**: references `e2e/inspect.mjs` (R-003-2), the Part 1 commands,
  the manual checklist format (contract), and the task convention (contract).
- **Validation rules**: self-contained (FR-003-002) — every command it names must
  exist in the repository; it must never instruct reading or writing the
  private vault (FR-003-010).

### Inspection helper

- **Shape**: a Node ESM CLI, `e2e/inspect.mjs` (R-003-2, R-003-3).
- **Operations**:
  - `eval <expression>` — evaluate JS in the page; print the value (JSON) to
    stdout.
  - `wait <css-selector> [--timeout <ms>]` — poll until the selector matches;
    default timeout 15 000 ms.
  - `screenshot <path>` — capture a PNG to the given path; print the path.
- **Common options**: `--port <number>` (default 9222, integer 1–65535).
- **Exit codes**: `0` success; `1` operation failed (wait timeout, page
  evaluation exception); `2` environment error before the operation ran (no
  CDP instance on the port). Every environment error includes the hint
  `(run npm run e2e:launch)`.
- **Validation rules**: no new external dependencies (FR-003-007); reuses
  `e2e/cdp.mjs` (FR-003-005); fail-fast with actionable errors (FR-003-006).
- **Full contract**: `contracts/inspect-cli.md`.

### Manual validation checklist

- **Shape**: a per-feature Markdown file under the feature's `checklists/`
  directory (e.g. `specs/<feature>/checklists/manual-validation.md`).
- **Fields (per scenario entry)**:
  - scenario id (e.g. `M1`, `M2`, …) and a short title;
  - mode: `automatable` | `subjective` | `live interaction` (FR-003-004);
  - status: `[ ]` pending / `[x]` pass / `[!]` fail / `[~]` pending user
    review;
  - evidence: a path to a committed screenshot (manual-assist) or a note that
    the automated evidence is in `e2e/output/` (gitignored);
  - the user's judgment or the agent's observation, one line.
- **State transitions**: `pending → pass | fail | pending user review`;
  `pending user review → pass | fail` only after the user's judgment is
  recorded. The agent MUST NOT move a subjective/live-interaction scenario to
  `pass`/`fail` on its own (spec edge case: user unavailable).
- **Validation rules**: screenshot persistence follows the hybrid rule (R-003-7);
  a `fail` entry must name the observed defect.
- **Full contract**: `contracts/manual-checklist-format.md`.

### Test vault fixtures

- **Shape**: committed Markdown notes under `test-vault/`.
- **Standard board (unchanged, Part 1)**: `Board.md` + `S1.md`–`S6.md` at the
  vault root; baseline in `contracts/test-vault-structure.md`
  (`taskColumns: 4`, 8 cards). This feature MUST NOT modify it.
- **Extended board (new, R-003-5)**: `test-vault/boards/Test Board 2.md` +
  `T1.md`–`T8.md` (names distinct from the root `S1`–`S6` — Obsidian
  wikilinks resolve vault-wide). Baseline in `contracts/extended-board-baseline.md`.
- **Validation rules**: both boards conform to
  `specs/001-user-story-map/contracts/board-file-format.md` and
  `story-file-format.md`; changing any fixture MUST update its baseline
  contract in the same change (spec edge case: fixture drift).

### Verification result record

- **Shape**: a checklist entry (above) plus, where prescribed, a screenshot
  artifact.
- **Persistence (R-003-7)**:
  - manual-assist screenshots → committed, `specs/<feature>/checklists/<scenario-id>-<slug>.png`;
  - automated-check screenshots → local, `e2e/output/` (gitignored).
- **Validation rules**: a record is complete only when status, evidence, and
  the one-line observation are all present.
